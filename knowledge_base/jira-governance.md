# Jira Governance Standard

## Purpose
This standard defines how Northstar Systems uses Jira for automation-related implementation work. The objective is to keep work items consistent enough for reporting, ownership, and handoff between business and technical teams.

## Approved Issue Types
Automation-related implementation work should normally use Task, Story, or Bug. New automation opportunities created by intake workflows should use **Task** unless the receiving project has an approved alternative.

## Approved Labels
Automated workflows may use only approved labels.

Department labels: `customer-support`, `sales`, `finance`, `hr`, `it-operations`.

Work-type labels: `ai-automation`, `process-improvement`, `knowledge-management`.

Stage labels: `discovery`, `pilot`, `production`.

Automated systems must not invent a new label because a similar label appears semantically appropriate. If a required label is missing from the approved list, the workflow should create the issue without the unsupported label and the platform owner should be asked to update governance if necessary.

## Statuses
The standard implementation workflow uses `To Do`, `In Progress`, `Blocked`, `In Review`, and `Done`.

Status changes represent actual work state and should not be generated by an LLM. Automations may transition issues only when the transition is explicitly allowed by the target project and the business rule is deterministic.

## Required Content
Automatically created implementation tasks should include a clear summary, the business request or relevant context, the recommendation, the proposed implementation approach, review status where applicable, important source documents or evidence, and a reviewer note when one exists.

The description should be concise enough for a delivery team to understand why the task exists without reopening the original intake form.

## Assignee Rules
Automated intake workflows should not guess an assignee based on free-text interpretation unless an approved deterministic routing rule exists. If no deterministic assignee rule is available, the task should remain unassigned or use the project default.

## Human Approval
If the intake process requires human approval, the Jira implementation task should only be created after approval. Rejected requests should be logged for traceability but must not create implementation tasks.

## Governance Enforcement
Some Jira rules are documented here for human understanding but should also be enforced technically. Examples include allowed label values, required issue type, required fields, and whether a rejected request is permitted to create a Jira issue.

Documentation alone is not sufficient enforcement for rules where the allowed behavior is exact and machine-checkable.

## Changes
Changes to approved labels, issue types, or standard statuses are owned by the Jira Platform Owner. Automation owners should not modify their workflow independently to introduce new governance values.
